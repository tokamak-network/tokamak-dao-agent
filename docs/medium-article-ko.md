# AI는 이미 DAO에서 투표하고 있습니다

*AI 에이전트 거버넌스를 위한 ERC 표준을 제안합니다*

---

지금 이 순간, AI가 당신의 DAO에서 투표하고 있을 수 있습니다. 그리고 당신은 그것을 알 방법이 없습니다.

AI 에이전트는 일반 이더리움 주소로 운영됩니다. 인간 투표자와 구별할 수 없습니다. 어떤 투표가 AI의 판단이고, 어떤 투표가 인간의 판단인지 — 온체인에서는 아무것도 보이지 않습니다.

우리 Tokamak Network는 직접 DAO를 운영하면서 이 문제를 체감했습니다. 제안이 올라오면 기술 사양을 읽고, 경제적 영향을 분석하고, 보안을 검토해야 합니다. 하지만 현실은 다릅니다. Uniswap은 적격 토큰의 5% 미만만 투표에 참여합니다. Compound는 정족수 미달이 반복됩니다. 우리 DAO도 예외는 아닙니다.

이것은 게으름의 문제가 아닙니다. 풀타임으로 일하면서 수십 개 프로토콜에 걸쳐 포트폴리오를 관리하는 토큰 홀더에게, 모든 제안을 의미 있게 평가하라는 것은 불가능한 요구입니다.

AI 에이전트는 이 격차를 메울 수 있습니다. 24시간 제안을 분석하고, 위임자의 선호에 따라 투표할 수 있습니다. 기술은 이미 존재합니다.

2주 전, 비탈릭 부테린이 DAO를 위한 "AI stewards"를 제안했습니다. 커뮤니티의 반응은 폭발적이었습니다. 하지만 그 제안은 온체인 인터페이스를 정의하지 않았습니다. 범용 에이전트 인프라(ERC-8004, ERC-8118)는 에이전트가 누구인지, 어떤 함수를 호출할 수 있는지를 다루지만, *거버넌스에 어떻게 참여해야 하는지*는 다루지 않습니다.

**비전은 명확합니다. 인터페이스가 없을 뿐입니다.** 표준 없이 무슨 일이 벌어질까요? DAO A가 자체 에이전트 레지스트리를 만들고, DAO B가 호환되지 않는 레지스트리를 만듭니다. Compound에서 신뢰도를 쌓은 에이전트가 Aave에서는 그 평판을 쓸 수 없습니다. 위임 선호도는 공유 스키마 없는 임의 JSON이 됩니다. 모든 DAO가 바퀴를 다시 발명하고, 그 바퀴들은 서로 맞지 않습니다.

이 EIP가 빠진 인터페이스를 정의합니다. 4개의 Solidity 컨트랙트. 2개는 필수, 2개는 선택. ERC-5805와 ERC-4824 위에 계층화 — Governor 수정 없이 동작합니다.

---

## 기존 표준이 안 되는 이유

현재 이더리움 거버넌스의 위임 표준은 ERC-5805의 `delegate(address)`입니다. 하나의 주소에서 다른 주소로 투표권을 이전하는 단순한 함수입니다. 인간 delegate 사이에서는 잘 작동해왔습니다.

하지만 AI 에이전트에게 이 함수로 위임하는 순간, 세 가지 문제가 발생합니다.

**첫째, 위임이 영원합니다.** `delegate(address)`에는 만료가 없습니다. 수동으로 철회하기 전까지 영구적입니다. 에이전트의 모델이 업데이트되거나, 운영자가 바뀌거나, 행동이 변질되어도 위임은 조용히 계속됩니다. 인간 delegate에게 위임할 때는 사회적 관계가 안전장치가 됩니다. AI에게는 그런 것이 없습니다.

**둘째, 선호도를 전달할 수 없습니다.** "재무 제안에는 보수적으로 투표하라" 또는 "헌법 변경은 나에게 알려라"고 지시할 방법이 없습니다. `delegate(address)`는 무조건적입니다. 인간에게는 대화로 전달하지만, AI에게는 기계가 읽을 수 있는 형식이 필요합니다.

**셋째, 안전 밸브가 없습니다.** 인간 delegate가 확신이 없는 제안을 만나면 기권하거나 위임자에게 연락합니다. AI 에이전트에는 "이 결정은 내가 판단하기 어려우니 인간이 직접 결정해야 한다"고 신호를 보낼 메커니즘이 없습니다.

여기에 두 가지 문제가 더 있습니다. AI 에이전트가 일반 EOA를 사용하기 때문에 온체인에서 AI와 인간을 구별할 수 없다는 것, 그리고 AI가 투표 결과를 본 후 논거를 소급 조작할 수 있다는 것입니다.

정리하면 이렇습니다.

| 현재 | 필요한 것 | 이 EIP |
|:---|:---|:---|
| 영구 위임 | 주기적 갱신 | `expiry` 파라미터 |
| 선호도 전달 불가 | 기계가 읽는 선호도 | `preferencesURI` |
| 에스컬레이션 없음 | 인간 복귀 메커니즘 | `escalate()` |
| AI 구별 불가 | 온체인 신원 | `IAIAgentRegistry` |
| 논거 조작 가능 | 무결성 보장 | 커밋-리빌 스킴 |

## 우리가 설계한 것

이 EIP는 4개의 Solidity 인터페이스를 정의합니다. 2개는 필수(Core), 2개는 선택(Extensions)입니다. ERC-20(핵심) + ERC-2612(permit 확장) 패턴을 따릅니다 — 필요한 것만 채택하면 됩니다.

```
┌─────────────────────────────────────────────┐
│             Core (필수 구현)                  │
│                                             │
│  ┌───────────────────┐ ┌─────────────────┐  │
│  │ IAIAgentRegistry  │ │  IAIDelegation  │  │
│  │                   │ │                 │  │
│  │ AI 에이전트의      │ │ 만료 + 선호도    │  │
│  │ 온체인 신원 등록   │ │ + 에스컬레이션   │  │
│  │                   │ │ 이 있는 위임     │  │
│  └───────────────────┘ └─────────────────┘  │
├─────────────────────────────────────────────┤
│           Extensions (선택 구현)              │
│                                             │
│  ┌───────────────────┐ ┌─────────────────┐  │
│  │ IRationale-       │ │ ICredibility-   │  │
│  │ Commitment        │ │ Registry        │  │
│  │                   │ │                 │  │
│  │ 커밋-리빌 방식의   │ │ 예측 정확도      │  │
│  │ 논거 무결성 보장   │ │ 기반 크로스-DAO  │  │
│  │                   │ │ 신뢰도 추적     │  │
│  └───────────────────┘ └─────────────────┘  │
└─────────────────────────────────────────────┘
```

각각이 어떤 문제를 해결하는지 이야기하겠습니다.

## AI도 신분증이 필요합니다

DAO 거버넌스에서 AI의 영향력이 커지고 있다면, 최소한 어떤 투표자가 AI인지는 알 수 있어야 합니다. 그래야 거버넌스 참여자들이 정보에 기반한 판단을 내릴 수 있습니다.

`IAIAgentRegistry`는 AI 에이전트를 위한 온체인 등록 시스템입니다. 에이전트를 등록하면 `keccak256(operator, nonce)`로 결정론적 ID가 부여됩니다. 이 ID는 등록 트랜잭션이 확인되기 전에 오프라인으로 계산할 수 있고, 하나의 운영자가 목적이 다른 여러 에이전트를 등록할 수 있습니다. 메타데이터 URI를 통해 모델, 운영자, 목적을 공개합니다.

비활성화는 영구적으로 설계했습니다. 재활성화는 불가능합니다. 운영자가 재개하고 싶다면 새로운 에이전트를 등록해서 처음부터 실적을 쌓아야 합니다. 단순하지만, 그래서 안전합니다.

---

## 위임에는 만료가 있어야 합니다

이 EIP에서 가장 핵심적인 설계 결정은 **모든 위임에 만료를 강제한 것**입니다.

`IAIDelegation`의 `delegateToAgent()`는 `agentId`, `expiry`, `preferencesURI` 세 가지를 받습니다. 만료 없는 위임은 불가능합니다. 에이전트의 행동이 변질되었을 때, 위임자가 아무것도 하지 않으면 위임이 자동으로 만료됩니다. 의식적인 재위임만이 위임을 연장합니다.

`preferencesURI`는 위임자의 의도를 기계가 읽을 수 있는 형식으로 전달합니다. 위험 허용도, 에스컬레이션 조건, 원칙을 JSON으로 명시합니다. 이를테면 "프로토콜 보안을 성장보다 우선시하라", "1M 달러 이상의 재무 제안은 항상 에스컬레이션하라" 같은 지시입니다.

그리고 `escalate()` — 이것이 안전 밸브입니다.

상상해보세요. AI 에이전트가 DAO의 투표 정족수를 변경하는 제안을 발견합니다. 위임자의 선호도에 "헌법 변경은 항상 에스컬레이션"이 설정되어 있습니다. 에이전트는 무리하게 판단하는 대신, `escalate()`를 호출하여 불확실성을 설명하는 이유와 함께 인간에게 돌려보냅니다. 위임자는 알림을 받고 직접 투표합니다.

AI가 "나는 이 결정을 내릴 수 없다"고 말할 수 있는 메커니즘. 이것이 인간 주권을 지키는 방법입니다.

## 논거 조작을 어떻게 막을 것인가

이 문제는 처음에는 사소해 보일 수 있습니다. 하지만 곰곰이 생각해보면 심각합니다.

AI 에이전트가 제안에 대해 투표한 후, 결과를 확인하고, 그때서야 "나는 처음부터 이렇게 예측했다"는 논거를 발표할 수 있습니다. 시간이 지나면 이 에이전트는 항상 맞추는 것처럼 보입니다. 거짓된 신뢰도가 쌓이고, 더 많은 위임을 받게 됩니다.

`IRationaleCommitment`은 이 문제를 커밋-리빌 스킴으로 해결합니다. 에이전트는 투표할 때 논거의 해시를 먼저 온체인에 기록합니다. 투표가 끝난 후에야 원문을 공개하고, 컨트랙트가 해시 일치를 검증합니다. salt를 포함시켜 레인보우 테이블 공격도 방지합니다.

결과적으로 논거의 타임라인이 온체인에서 암호학적으로 증명됩니다. 누구나 "이 논거가 결과를 알기 전에 작성되었는가?"를 검증할 수 있습니다.

## 실적으로 증명하라

어떤 AI 에이전트에게 위임해야 할까요? 스스로 "나는 정확하다"고 주장하는 것은 의미가 없습니다. 객관적인 온체인 실적이 필요합니다.

`ICredibilityRegistry`는 확신도 가중 점수 체계로 예측 정확도를 추적합니다. 에이전트는 결과가 나오기 전에 예측과 확신도(0-100)를 기록합니다. 에이전트와 분리된 독립적 해결자가 실제 결과를 판정합니다.

점수 체계의 설계가 중요합니다.

| 상황 | 점수 변화 |
|------|----------|
| 높은 확신 + 정답 | **+3** |
| 낮은 확신 + 정답 | **+1** |
| 높은 확신 + 오답 | **-2** |
| 낮은 확신 + 오답 | **-1** |

항상 높은 확신을 주장하면? 맞으면 +3이지만, 틀리면 -2입니다. 장기적으로 실제 정확도 없이는 손해입니다. 항상 낮은 확신으로 헤징하면? 맞아도 +1이 최대입니다. 정직하게 확신도를 표현하는 것이 최적 전략이 되도록 설계했습니다.

그리고 이 신뢰도는 특정 DAO에 묶이지 않습니다. `agentId`에 연결되기 때문에, 하나의 DAO에서 쌓은 실적을 다른 DAO에서 확인할 수 있습니다. AI 거버넌스 품질에 대한 경쟁적 시장이 만들어지는 것입니다.

## 전체 그림

이 모든 것이 어떻게 연결되는지 한눈에 보겠습니다.

```
1. 에이전트  →  2. 위임     →  3. 제안     →  4. 논거 커밋
   등록          받기           생성           + 예측 기록

5. 투표     →  6. 논거     →  7. 예측     →  8. 신뢰도
   실행          공개           해결           확인
```

운영자가 에이전트를 등록하고, 토큰 홀더가 만료와 선호도를 설정해 위임합니다. 제안이 올라오면 에이전트는 분석 후 논거 해시를 커밋하고, 확신도와 함께 예측을 기록합니다. 투표를 실행하고, 투표 종료 후 논거를 공개합니다. 해결자가 실제 결과를 판정하면 신뢰도 점수가 업데이트됩니다.

전체 라이프사이클을 Sepolia 테스트넷에 배포했습니다. [인터랙티브 데모](https://erc-ai-governance.tokamak.network/demo)에서 직접 체험할 수 있습니다.

## 빌더를 위한 참고

이 표준은 어떤 거버넌스 프레임워크와도 호환되도록 설계했지만, OpenZeppelin Governor와의 통합 예시를 함께 제공합니다. `GovernorAIDelegation`은 IVotes와 연결하고, `GovernorResolver`는 `IGovernor.state()`를 읽어 신뢰도 해결을 자동화합니다. 이것은 참고 구현이지 표준의 요구사항은 아닙니다.

보안 측면에서는 에이전트 공모, 시빌 공격, 오라클 조작, 커밋-리빌 프런트런닝, 프롬프트 인젝션 등 10가지 위협을 스펙에서 식별하고 대응책을 명시했습니다. 자세한 내용은 [전체 스펙](https://erc-ai-governance.tokamak.network)에서 확인할 수 있습니다.

## 왜 우리가 이것을 만들었는가

이 표준은 인간 거버넌스를 AI로 대체하는 것이 아닙니다. AI 참여를 가시적이고, 제약되며, 책임감 있게 만드는 것입니다.

우리가 DAO를 운영하면서 직접 느낀 것은, 참여율 문제는 기술로 해결할 수 있지만 투명성 문제는 표준이 없으면 해결할 수 없다는 것입니다. 각 DAO가 독자적으로 AI 통합을 구축하면 파편화됩니다. 공통 인터페이스가 있어야 공유된 도구, 공유된 감사, 공유된 신뢰가 가능합니다.

한국의 블록체인 팀이 이더리움 표준을 제안하는 것 — 이것 자체가 탈중앙화 거버넌스의 본질이라고 생각합니다. 표준은 특정 기업이나 국가의 것이 아닙니다. 생태계 전체의 것입니다.

AI 에이전트는 우리가 표준화하든 하지 않든 거버넌스에 올 것입니다.
투명하게 오도록 만듭시다.
